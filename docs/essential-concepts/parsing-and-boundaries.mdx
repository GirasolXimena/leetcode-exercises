# Parsing and Boundary Conditions

## Parsing in stages

Parsing turns an input representation, such as text, into a value a program can use. A clear parser makes its rules visible in stages:

1. Skip permitted leading whitespace.
2. Read an optional sign.
3. Read consecutive digits.
4. Stop at the first character that is not a digit.
5. Apply the allowed numeric range.

This makes inputs such as `"  -42abc"`, `"+7"`, and `"words"` predictable instead of relying on a large implicit conversion.

## Boundaries are normal inputs

An edge case is not necessarily an invalid case. Empty arrays, one-item arrays, zero, a full rotation, the smallest allowed integer, and the largest allowed integer often exercise a different branch of the algorithm.

A useful boundary test asks:

- What happens before the first element?
- What happens after the last element?
- What happens when the input is empty?
- What happens at the minimum and maximum allowed values?
- What happens when a carry, sign, or loop reaches its limit?

## Avoid truthiness for numeric meaning

In JavaScript, `0` is falsy. A condition such as `if (!digits[index])` cannot distinguish a missing value from a real zero. Use an explicit structural check such as `index === 0` when you mean “this is the first position.”

The [Plus One](../array/plus-one) exercise uses this distinction when a carry reaches the first digit. The [Palindrome Number](../number/palindrome-number) exercise checks the signed 32-bit range before processing digits, and [String to Integer](../string/my-atoi) normalizes signed zero after parsing.

Boundary-focused tests are cheap and often expose bugs that ordinary examples do not.
